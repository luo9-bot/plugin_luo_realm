# Luo Realm 注册门禁与视觉复刻设计

## 目标

修正当前“执行任意玩法命令都会隐式创建玩家”的行为，将 Luo Realm 改为明确的两阶段入世流程，
并以原 SUB.H 插件素材和信息层级为视觉依据，重做角色卡与决斗 GIF。

本阶段只处理注册、体系确定、玩法门禁、角色卡和玩家决斗。装备、商城、任务、BOSS 和地图仍按
既有路线后续实现，不在本次改动中创建空接口。

## 逆向依据

旧插件逆向报告表明，SUB.H 的核心循环是“个人形象、等级、阶级、属性、技能与装备培养，再参与
玩家 PK 和世界 BOSS”，而不是收到命令后自动生成默认角色。旧版查询页以形象、阶级卡片、等级、
货币和战斗统计为主要信息；战斗展示包含双方形象、生命值、技能和逐步动画。

本设计保留这些信息层级，移除旧授权和 INI 数据结构，并继续使用 SQLite、修行体系、境界、机缘和
完整战力公式。

## 注册状态

在 `players` 表增加 `registration_state`：

- `pending_system`：已登记名称，但尚未确定修行体系。
- `active`：已确定初始体系，角色可参与世界玩法。

迁移前已经存在的玩家默认设为 `active`，保证旧导入数据和现有 LR 数据继续可用。`players.status`
仍表示管理状态 `active / disabled / deleted`，不得与注册阶段混用。

注册流程：

1. `注册 <名称>` 在单个事务中创建 `players` 和 `player_profiles`，注册状态为 `pending_system`。
2. 注册成功后返回十一种体系及 `选择体系 <标识>` 提示，不创建钱包奖励、签到或修行收益。
3. `选择体系 <标识>` 仅允许 `pending_system` 玩家执行；在单个事务中创建
   `player_cultivation` 并将注册状态更新为 `active`。
4. 已激活玩家不能免费重选体系。未来的转修必须是单独的带代价玩法。
5. `改名 <名称>` 对 `pending_system` 和 `active` 玩家开放；不存在的玩家会收到注册提示。

名称去除首尾空白，长度限制为 1 至 20 个 Unicode 字符，拒绝控制字符。名称不要求全局唯一，
玩家身份始终由 QQ 号确定。

## 命令门禁

消息先通过群白名单或管理员私聊检查，再解析命令，最后查询注册阶段。注册查询不得写数据库。

| 玩家状态 | 允许命令 |
| --- | --- |
| 不存在 | 菜单、体系、注册 |
| `pending_system` | 菜单、体系、选择体系、改名 |
| `active` | 所有已实现玩法命令 |
| 管理禁用或删除 | 仅返回角色不可用提示 |

未注册玩家使用玩法命令时返回：`尚未注册，请发送“注册 <名称>”创建角色。`

待选玩家使用玩法命令时返回：`角色尚未确定修行体系，请发送“体系”查看并选择。`

门禁统一放在命令分发入口，不在签到、事件、查询和决斗分支分别复制。任何普通玩法函数不得调用
`find_or_create`。注册是唯一允许创建普通玩家的机器人命令。

## 决斗约束

`决斗 <QQ>` 的发起者必须已激活。目标玩家通过只读查询加载，并同时满足：

- 玩家存在；
- `registration_state = active`；
- `players.status = active`；
- 已存在修行体系记录；
- 目标不是发起者本人。

任一条件不满足时返回明确提示，不创建目标玩家，不写战斗记录，不改变钱包和统计。双方校验、战斗
记录、奖励和统计继续在同一个 `BEGIN IMMEDIATE` 事务中完成。

## 数据访问边界

`database::player` 提供明确接口：

- `registration_state`：只读检查玩家不存在、待选、激活或不可用。
- `register`：只创建待选玩家及资料。
- `activate_system`：只完成首次体系选择。
- `get_active`：加载已激活角色；状态不符返回领域结果，不隐式创建。
- `rename`：只修改已存在且未删除的角色。

旧 `find_or_create` 从机器人玩法路径移除。离线迁移和管理工具如需显式创建数据，应调用专用导入或
管理接口，不复用玩家注册命令。

## 角色卡

角色卡恢复旧插件“形象是主体，数据围绕形象排列”的结构：

- 左侧使用 `SUBData/SUB-图片/形象图片` 中的角色素材；按玩家稳定种子选择默认形象，确保重启不变。
- 右侧显示名称、QQ、体系、当前境界、综合战力、生命、攻击、防御、速度、金币、刻印和胜负。
- 顶部使用体系专属强调色，底部显示境界进度和机缘修正。
- 可用时叠加 `阶级图片/<realm_index>.png`；素材缺失时降级为纯色徽记，不导致查询失败。

渲染器接收完整 `ProfileRenderData`，不得从数据库自行查询。素材根目录优先使用插件目录下
`assets/legacy`；开发与迁移阶段允许回退到相邻 `SUBData/SUB-图片`。部署文档说明需要复制的素材。

## 决斗 GIF

战斗画面使用横向双边竞技布局：

- 双方形象位于左右两侧，名称、体系、境界和战力紧邻形象。
- 顶部生命条根据真实逐回合生命变化，而不是用最终胜负线性推算。
- 中央显示回合数、伤害、暴击、闪避和当前技能；底部保留简短战报。
- 胜负帧突出获胜方并显示奖励，最后停留两帧方便群聊客户端阅读。

因此 `CombatResult` 扩展为包含逐回合帧，每个动作至少记录攻击者、技能、伤害、是否暴击和双方剩余
生命。数据库已有 `combat_rounds.frame_json`，决斗记录在同一事务中保存帧数据。GIF 上限保留合理
帧数，但不得丢失数据库中的完整战报。

旧素材只作为形象、阶级、技能图标和特效来源，不延续旧版文字、付费标识或固定数值。素材加载失败
时使用 LR 内置的几何占位画面，并继续返回文字战报。

## 字体与部署

目标运行平台是 Windows。渲染器优先读取插件配置指定字体，其次尝试系统中文字体。字体或素材不可用
时不得让玩法事务回滚：数据库战斗先提交，图片渲染失败则返回完整文本战报并记录错误。

动态图片写入 `data/luo_realm/cards` 和 `data/luo_realm/battles`。文件名包含玩家或战斗标识，使用临时
文件完成编码后再替换目标文件，防止中断留下半张 PNG/GIF。

## 后台管理兼容

玩家列表与详情增加注册阶段。待选玩家可由管理员修正名称，但后台修改修行体系时必须同步激活注册
阶段；删除或禁用状态继续优先于注册阶段。概览分别展示待选和激活玩家数量。

## 错误与事务

- 重复注册：返回已经注册或待选体系提示，不覆盖名称和数据。
- 非法名称或体系：事务不写入任何记录。
- 体系激活中断：玩家保持 `pending_system`，不会出现已激活但缺修行记录的状态。
- 决斗任一方无效：事务不写战斗、奖励和统计。
- 图片渲染失败：已提交的业务结果保留，返回文字数据，不伪报战斗失败。

## 验收标准

1. 未注册用户执行签到、查询、战力、事件、排行、改名或决斗时，不产生玩家及领域数据，并收到注册提示。
2. `注册 名称` 后只有玩家与资料数据，签到仍被拒绝；改名可用。
3. 首次选择有效体系后角色激活，重复选择被拒绝。
4. 决斗双方任一未注册、待选、禁用或缺少修行记录时不产生战斗记录和奖励。
5. 旧数据库升级后已有玩家保持可玩。
6. 角色卡和战斗 GIF 使用旧素材；素材或字体缺失时文字结果仍完整。
7. `cargo fmt --check`、Clippy 零警告、完整测试和 release 构建通过。
